# S3

## **Question 1**

There was an incident in a production environment where user data stored in an Amazon S3 bucket was accidentally deleted by a Junior DevOps Engineer. The issue was escalated to management, and after a few days, an instruction was given to improve the security and protection of AWS resources.

What combination of the following options will protect the S3 objects in the bucket from both accidental deletion and overwriting? (Select TWO.)

**Options:**

- Provide access to S3 data strictly through pre-signed URL only
- Enable Versioning
- Disallow S3 Delete using an IAM bucket policy
- Enable Multi-Factor Authentication Delete
- Enable S3 Intelligent-Tiering

<details>
<summary><strong>Answer & Explanation</strong> 📝</summary>
By using Versioning and enabling MFA (Multi-Factor Authentication) Delete, you can secure and recover your S3 objects from accidental deletion or overwrite.

Hence, the correct answers are:

- Enable Versioning
- Enable Multi-Factor Authentication Delete

<span style="color:red"><strong>The option that says: Providing access to S3 data strictly through pre-signed URL only is incorrect</strong></span> since a pre-signed URL gives access to the object identified in the URL. Pre-signed URLs are useful when customers perform an object upload to your S3 bucket, but does not help in preventing accidental deletes.

<span style="color:red"><strong>The option that says: Disallowing S3 Delete using an IAM bucket policy is incorrect</strong></span> since you still want users to be able to delete objects in the bucket, and you just want to prevent accidental deletions. Disallowing S3 Delete using an IAM bucket policy will restrict all delete operations to your bucket.

<span style="color:red"><strong>The option that says: Enabling S3 Intelligent-Tiering is incorrect</strong></span> since S3 intelligent tiering does not help in this situation.

</details>

## **Question 2**

A company collects atmospheric data such as temperature, air pressure, and humidity from different countries. Each site location is equipped with various weather instruments and a high-speed Internet connection. The average collected data in each location is around 500 GB and will be analyzed by a weather forecasting application hosted in Northern Virginia. The Solutions Architect must determine the fastest way to aggregate all the data.

Which of the following options can satisfy the given requirement?

**Options:**

- Set up a Site-to-Site VPN connection.
- Upload the data to the closest Amazon S3 bucket. Set up a cross-region replication and copy the objects to the destination bucket.
- Enable Transfer Acceleration in the destination bucket and upload the collected data using Multipart Upload.
- Use AWS Snowball Edge to transfer large amounts of data.

<details>
<summary><strong>Answer & Explanation</strong> 📝</summary>
Amazon S3 is object storage built to store and retrieve any amount of data from anywhere on the Internet. It’s a simple storage service that offers industry-leading durability, availability, performance, security, and virtually unlimited scalability at very low costs. Amazon S3 is also designed to be highly flexible. Store any type and amount of data that you want; read the same piece of data a million times or only for emergency disaster recovery; build a simple FTP application or a sophisticated web application.

<img src="https://media.tutorialsdojo.com/s3_ta_speed_compare_2.png"
     alt="S3 Transfer Acceleration speed comparison"
     width="600" />

Since the weather forecasting application is located in N.Virginia, you need to transfer all the data in the same AWS Region. With Amazon S3 Transfer Acceleration, you can speed up content transfers to and from Amazon S3 by as much as 50-500% for long-distance transfer of larger objects. Multipart upload allows you to upload a single object as a set of parts. After all the parts of your object are uploaded, Amazon S3 then presents the data as a single object. This approach is the fastest way to aggregate all the data.

### 🟢 **Correct Answer**

**Enable Transfer Acceleration in the destination S3 bucket and upload the collected data using Multipart Upload.**

This is the **fastest way** to transfer large amounts of data to an S3 bucket across long distances.
**S3 Transfer Acceleration** uses Amazon CloudFront edge locations to speed up uploads, while **Multipart Upload** optimizes large object transfers for efficiency and resilience.

### 🛑 **Incorrect Options Explained**

<span style="color:red"><strong>#### ❌ Upload to the closest S3 bucket and use Cross-Region Replication</strong></span>

- S3 Cross-Region Replication (CRR) typically has a delay of **~15 minutes**.
- The scenario requires **fastest possible aggregation**, not delayed eventual consistency.

<span style="color:red"><strong>#### ❌ Use AWS Snowball Edge</strong></span>

- Snowball Edge requires **ordering the device**, **shipping**, **loading data**, and **return shipping**.
- Even for 80 TB, the total turnaround time is **approximately one week**, far too slow for the scenario.

<span style="color:red"><strong>#### ❌ Set up a Site-to-Site VPN connection</strong></span>

- VPN is for **secure connectivity** between on-premises networks and AWS VPC — not S3 optimization.
- Does **not** accelerate data uploads.
- Not the fastest option for bulk data transfer.

### 🧠 **Summary**

To move large amounts of data into Amazon S3 **as quickly as possible**, the combination of:

- **S3 Transfer Acceleration**
- **Multipart Upload**

is the most effective and AWS-recommended approach.

</details>

## **Question 3**

For data privacy, a healthcare company has been asked to comply with the Health Insurance Portability and Accountability Act (HIPAA). The company stores all its backups on an Amazon S3 bucket. It is required that data stored on the S3 bucket must be encrypted.

What is the best option to do this? (Select TWO.)

**Options:**

- Store the data in encrypted Amazon EBS snapshots.
- Store the data on Amazon EBS volumes with encryption enabled instead of using S3.
- Before sending the data to S3 over HTTPS, encrypt the data locally first using your own encryption keys.
- Enable Server-Side Encryption on an S3 bucket to make use of AES-128 encryption.
- Enable Server-Side Encryption on an S3 bucket to make use of AES-256 encryption.

<details>
  <summary><strong>Answer & Explanation</strong> 📝</summary>

Server-side encryption is about data encryption at rest—that is, Amazon S3 encrypts your data at the object level as it writes it to disks in its data centers and decrypts it for you when you access it. As long as you authenticate your request and you have access permissions, there is no difference in the way you access encrypted or unencrypted objects. For example, if you share your objects using a pre-signed URL, that URL works the same way for both encrypted and unencrypted objects.

You have four mutually exclusive options depending on how you choose to manage the encryption keys:

1. Use Server-Side Encryption with Amazon S3-Managed Keys (SSE-S3)
2. Use Server-Side Encryption with AWS KMS Keys (SSE-KMS)
3. Use dual-layer Server-Side Encryption with AWS KMS Keys (DSSE-KMS) — added in 2023
4. Use Server-Side Encryption with Customer-Provided Keys (SSE-C)

### 🟢 **Correct Answers**

1. **Before sending the data to S3 over HTTPS, encrypt the data locally using your own encryption keys.**

   - This refers to **Client-Side Encryption**, where you encrypt data **before** uploading it.
   - Ensures that **you control the encryption keys** and that data stays encrypted end-to-end.

2. **Enable Server-Side Encryption (SSE) on the S3 bucket using AES-256.**

   - This enables **SSE-S3**, where Amazon S3 handles encryption at rest using **AES-256**, the only supported AES option for SSE.
   - Provides seamless encryption without requiring key management on your side.

These two methods together ensure **maximum data protection** both before upload and once stored in S3.

### 🔴 **Incorrect Options Explained**

<span style="color:red"><strong>#### ❌ Store the data on encrypted Amazon EBS volumes instead of S3</strong></span>

- EBS is **block storage**, not object storage.
- The scenario explicitly requires storing data in **Amazon S3**, not EBS.
- EBS encryption does **not** apply to S3 workloads.

<span style="color:red"><strong>#### ❌ Store the data in encrypted Amazon EBS snapshots</strong></span>

- EBS snapshots are backups of EBS volumes and still tied to **block storage**.
- This does **not** fulfill the requirement for encryption on **S3 object storage**.

<span style="color:red"><strong>#### ❌ Enable AES-128 Server-Side Encryption in S3</strong></span>

- Amazon S3 **does not support AES-128** for SSE.
- **Only AES-256** is supported for S3 server-side encryption (SSE-S3).
- Therefore, AES-128 is not an option in S3.

### 🧠 **Summary**

To securely upload and store sensitive data in S3:

- ✔ Encrypt data **before upload** using your own keys.
- ✔ Enable **SSE-S3** with **AES-256** for encryption at rest.
- ❌ Do not use EBS storage or snapshots — they are unrelated to S3.
- ❌ AES-128 encryption is **not supported** by S3.

</details>

## **Question 4**

**There are a few, easily reproducible but confidential files that your client wants to store in AWS without worrying about storage capacity. For the first month, all of these files will be accessed frequently, but after that, they will rarely be accessed. The old files will only be accessed by developers, so there is no set retrieval time requirement. However, the files under a specific dojo-finance prefix in the S3 bucket will be used for post-processing that requires millisecond retrieval time.**

**Given these conditions, which of the following options would be the most cost-effective solution for your client’s storage needs?**

- 🅐 Store the files in S3, then after a month, change the storage class of the dojo-finance prefix to S3-IA while the remaining objects move to S3 Glacier using a lifecycle policy.
- 🅑 Store the files in S3, then after a month, change the storage class of the entire bucket to S3 Intelligent-Tiering using a lifecycle policy.
- 🅒 Store the files in S3, then after a month, change the storage class of the entire bucket to S3-IA using a lifecycle policy.
- 🅓 Store the files in S3, then after a month, change the storage class of the dojo-finance prefix to One Zone-IA while the remaining objects move to S3 Glacier using a lifecycle policy.

<details>
  <summary><strong>Answer & Explanation</strong> 📝</summary>

Note: **S3-IA** costs more than **S3 One Zone-IA**.  Given the files are easily reproducible, **One Zone-IA** is the cheaper, acceptable choice.

Amazon S3 provides storage-class lifecycle transition capabilities that help you optimize costs. For data that becomes infrequently accessed after a month and is easily reproducible, you can tier storage to less expensive classes. **S3 One Zone-IA** offers lower cost for infrequently accessed data that can be recreated if lost, while **Glacier** (or Glacier Flexible Retrieval/Deep Archive depending on retrieval needs) provides very low-cost long-term archival.


Initially, the files will be accessed frequently, and S3 is a durable and highly available storage solution for that. After a month has passed, the files won’t be accessed frequently anymore, so it is a good idea to use lifecycle policies to move them to a storage class that would have a lower cost for storing them.

<img src="https://media.tutorialsdojo.com/public/lifecycle-transitions-v2.png"
     alt="S3 lifecycle transitions diagram"
     width="600" />

Since the files are easily reproducible and some of them are needed to be retrieved quickly based on a specific prefix filter (tdojo-finance), S3-One Zone IA would be a good choice for storing them. The other files that do not contain such prefix would then be moved to Glacier for low-cost archival. This setup would also be the most cost-effective for the client.

<img src="https://media.tutorialsdojo.com/public/2019-04-02_04-26-21-158b6e1eb7ef7be3b91049e88f056f3a.gif"
     alt="S3 lifecycle animation"
     width="600" />

**Hence, the correct answer is:** <span style="color:green"><strong>Store the files in S3 then after a month, change the storage class of the <em>tdojo-finance</em> prefix to One Zone-IA while the remaining go to Glacier using lifecycle policy.</strong></span>

<strong>Incorrect options explained:</strong>

* <span style="color:red"><strong>Storing the files in S3 then after a month, changing the storage class of the bucket to S3-IA using lifecycle policy</strong></span> is incorrect because, although moving files to **S3-IA** is valid, **S3-IA** is more expensive than **S3 One Zone-IA**. Given the files are easily reproducible, **One Zone-IA** is the cheaper, acceptable choice.

* <span style="color:red"><strong>Storing the files in S3 then after a month, changing the storage class of the bucket to Intelligent-Tiering using lifecycle policy</strong></span> is incorrect because **S3 Intelligent-Tiering** is designed for unknown or changing access patterns and needs time to analyze usage. Since you **already know** these files become infrequently accessed after one month, an immediate lifecycle transition to a specific lower-cost class (One Zone-IA and Glacier) is more cost-effective.

* <span style="color:red"><strong>Storing the files in S3 then after a month, changing the storage class of the <em>tdojo-finance</em> prefix to S3-IA while the remaining go to Glacier using lifecycle policy</strong></span> is incorrect because **S3-IA** still costs more than **S3 One Zone-IA**. Since the files are easily reproducible, **One Zone-IA** is preferable to further reduce cost while accepting the single-AZ durability tradeoff.

</details>
