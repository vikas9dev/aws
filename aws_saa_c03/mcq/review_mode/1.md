## ❓ Why does EC2 not show memory metrics by default, but RDS does?

<details>
<summary><strong>Explanation</strong> 📝</summary>

### ✅ Amazon EC2 (Compute Instances)

* **Memory metrics are NOT available by default** in **Amazon CloudWatch**
* Reason:

  * EC2 is **customer-managed**
  * AWS can only see **hypervisor-level metrics**
  * Memory (RAM) is inside the **guest operating system**
* To get memory metrics:

  * Install **CloudWatch Agent**
  * Publish them as **custom metrics** (billable)

**📌 Example:**
You must create a custom metric to monitor EC2 RAM usage.

### ✅ Amazon RDS (Managed Database)

* **Memory metrics ARE available by default**
* Reason:

  * RDS is a **fully managed service**
  * AWS controls the **OS and database engine**
* Memory metrics available automatically:

  * **FreeableMemory**
  * SwapUsage
  * DatabaseMemoryUsagePercentage

**📌 Example:**
You can directly view `FreeableMemory` in CloudWatch without installing anything.

### 🔍 Quick comparison

| Service        | Memory Metrics by Default | Why                     |
| -------------- | ------------------------- | ----------------------- |
| **Amazon EC2** | ❌ No                      | OS is customer-managed  |
| **Amazon RDS** | ✅ Yes                     | OS & DB are AWS-managed |

### 🧠 One-line exam takeaway

> **EC2 requires custom CloudWatch metrics for memory because AWS doesn’t manage the OS, while RDS provides memory metrics by default because it’s a fully managed service.**

</details>

## Question 2

**An online cryptocurrency exchange platform is hosted in AWS, utilizing an Amazon ECS cluster and Amazon RDS in a Multi-AZ deployment configuration. The application heavily uses the RDS instance to process complex read and write database operations. To maintain reliability, availability, and performance, it is necessary to closely monitor how the different processes or threads on a DB instance use the CPU, including the percentage of CPU bandwidth and total memory consumed by each process.**

**Which of the following is the most suitable solution to monitor the database properly?**

- 🅐 Check the CPUs and MEMs metrics which are readily available in the RDS console that show the percentage of the CPU bandwidth and total memory consumed by each database process of your RDS instance.
- 🅑 Use Amazon CloudWatch to monitor the CPU Utilization of your database.
- 🅒 Create a script that collects and publishes custom metrics to Amazon CloudWatch, which tracks the real-time CPU utilization of the RDS instance, and then set up a custom CloudWatch dashboard to view the metrics.
- 🅓 Enable Enhanced Monitoring in RDS.

<details>
<summary><strong>Answer & Explanation</strong> 📝</summary>

### ✅ Correct Answer: 🅓

**Enable Enhanced Monitoring in RDS.**

### Explanation

The requirement is to:

- Monitor **per-process / per-thread CPU usage**
- See **CPU bandwidth percentage** and **memory consumption by each process**
- Gain **deep, OS-level visibility** into the RDS instance

**Amazon RDS Enhanced Monitoring** is specifically designed for this purpose.

When enabled, Enhanced Monitoring:

- Provides **real-time OS-level metrics** (as granular as 1-second intervals)
- Shows **per-process and per-thread CPU usage**
- Displays **memory, file system, and load information** by process
- Sends detailed metrics to **CloudWatch Logs**, viewable in the RDS console

This level of detail is **not available** through standard CloudWatch metrics.

### Why the other options are incorrect

- ❌ **🅐 CPU and MEM metrics in the RDS console**
  These metrics do **not** show per-process or per-thread resource usage.

- ❌ **🅑 CloudWatch CPU Utilization**
  CloudWatch provides **instance-level metrics only**, not process-level visibility.

- ❌ **🅒 Custom scripts publishing metrics**
  You **cannot install custom agents or scripts** on managed RDS instances to collect OS-level process metrics.

### Key takeaway 📌

When you need **deep visibility into database instance internals**, including **per-process CPU and memory usage**, the correct and AWS-recommended solution is:

👉 **Amazon RDS Enhanced Monitoring**

Amazon RDS offers a powerful feature known as Enhanced Monitoring, which provides detailed metrics in real-time about the operating system (OS) underlying your database instances. This feature allows users to monitor performance at a granular level through the AWS Management Console or by accessing the Enhanced Monitoring JSON output via CloudWatch Logs. By default, these metrics are retained in CloudWatch Logs for 30 days, but this retention period can be adjusted by modifying the retention settings for the RDSOSMetrics log group in CloudWatch.

<img src="https://media.tutorialsdojo.com/public/TD-RDSEnhancedMonitoring-12June2025.png"
     alt="Amazon RDS Enhanced Monitoring"
     width="600" />

Enhanced Monitoring differs from standard CloudWatch metrics in that it gathers data directly from an agent installed on the instance, rather than from the hypervisor, which is used by CloudWatch. This distinction can lead to slight variations between the two sets of metrics. For instance, CloudWatch provides CPU utilization metrics based on the hypervisor’s view, while Enhanced Monitoring captures detailed insights from the instance itself, offering a more accurate representation of resource usage at the OS level.

This feature is particularly beneficial for users who need in-depth visibility into how individual processes or threads on a DB instance utilize CPU resources. The differences in metric data may become more pronounced when using smaller instance classes, as multiple virtual machines are often managed by the same hypervisor, affecting the accuracy of hypervisor-based metrics.

Hence, the correct answer is: Enable Enhanced Monitoring in RDS.

The option that says: Using Amazon CloudWatch to monitor the CPU Utilization of your database is incorrect. Although you can use this to monitor the CPU Utilization of your database instance, it does not provide the percentage of the CPU bandwidth and total memory consumed by each database process in your RDS instance. Take note that CloudWatch primarily gathers metrics about CPU utilization from the hypervisor for a DB instance while RDS Enhanced Monitoring gathers its metrics from an agent on the instance.

The option that says: Create a script that collects and publishes custom metrics to Amazon CloudWatch, which tracks the real-time CPU Utilization of the RDS instance, and then set up a custom CloudWatch dashboard to view the metrics is incorrect. Although you can use Amazon CloudWatch Logs and CloudWatch dashboard to monitor the CPU Utilization of the database instance, using CloudWatch alone is just not enough to get the specific percentage of the CPU bandwidth and total memory consumed by each database processes. The data provided by CloudWatch is not as detailed as compared with the Enhanced Monitoring feature in RDS. Take note as well that you do not have direct access to the instances/servers of your RDS database instance, unlike with your EC2 instances where you can install a CloudWatch agent or a custom script to get CPU and memory utilization of your instance.

The option that says: Check the CPU% and MEM% metrics which are readily available in the RDS console that shows the percentage of the CPU bandwidth and total memory consumed by each database process of your RDS instance is incorrect because the CPU% and MEM% metrics are not readily available in the Amazon RDS console, which is contrary to what is being stated in this option.

</details>

## Question 3

**A software development company is using serverless computing with AWS Lambda to build and run applications without having to set up or manage servers. The company has a Lambda function that connects to a MongoDB Atlas database and also uses a third-party API. A developer was instructed to create environment variables for the MongoDB hostname, username, password, and API credentials for DEV, SIT, UAT, and PROD environments.**

**Considering that the Lambda function is storing sensitive database and API credentials, how can this information be secured to prevent other developers, or anyone else, from seeing these credentials in plain text? Select the best option that provides maximum security.**

- 🅐 There is no need to do anything because, by default, Lambda already encrypts the environment variables using AWS Key Management Service.
- 🅑 Create a new AWS KMS key and use it to enable encryption helpers that leverage AWS Key Management Service to store and encrypt the sensitive information.
- 🅒 Enable SSL encryption that leverages AWS CloudHSM to store and encrypt the sensitive information.
- 🅓 Lambda does not provide encryption for the environment variables. Deploy your code to an Amazon EC2 instance instead.

<details>
<summary><strong>Answer & Explanation</strong> 📝</summary>

### ✅ Correct Answer: 🅑

**Create a new AWS KMS key and use it to enable encryption helpers that leverage AWS Key Management Service to store and encrypt the sensitive information.**

### Explanation

The key requirements are:

- Protect **sensitive credentials** (DB username/password, API keys)
- Prevent **other developers** from viewing secrets in plain text
- Provide **maximum security**
- Work natively with **AWS Lambda**

### Why 🅑 is the best and most secure option

Although AWS Lambda **does encrypt environment variables by default**, maximum security is achieved by:

- Using a **customer-managed AWS KMS key (CMK)** instead of the default AWS-managed key
- Applying **fine-grained IAM permissions** to control who can decrypt the secrets
- Ensuring that **only the Lambda execution role** can use `kms:Decrypt`

This approach:

- Encrypts secrets **at rest** using envelope encryption
- Protects secrets from unauthorized access in the console, CLI, or API
- Provides **audit logs** via AWS CloudTrail showing when and by whom the KMS key was used

### Why the other options are incorrect

- ❌ **🅐 “Do nothing”**
  While Lambda does encrypt environment variables by default, **developers with sufficient IAM permissions can still view them**. This does **not provide maximum security**.

- ❌ **🅒 SSL + CloudHSM**
  SSL protects data **in transit**, not secrets stored in Lambda environment variables. CloudHSM is unnecessary and overly complex for this use case.

- ❌ **🅓 Deploy to EC2**
  Incorrect. Lambda **does support encryption** for environment variables and is more secure and manageable than EC2 for this scenario.

### Best practice note 📌

In real-world architectures, AWS also recommends:

- **AWS Secrets Manager** or **AWS Systems Manager Parameter Store (SecureString)**
  for managing secrets instead of environment variables.
  However, based strictly on the provided options, **AWS KMS with customer-managed keys** is the correct and most secure choice.

### 🧠 Key takeaway 📌

For securing sensitive credentials in AWS Lambda with **maximum security and control**:

👉 **Use a customer-managed AWS KMS key to encrypt environment variables and restrict decryption access**

When you create or update Lambda functions that use environment variables, AWS Lambda encrypts them using the AWS Key Management Service. When your Lambda function is invoked, those values are decrypted and made available to the Lambda code.

The first time you create or update Lambda functions that use environment variables in a region, a default service key is created for you automatically within AWS KMS. This key is used to encrypt environment variables. However, if you wish to use encryption helpers and use KMS to encrypt environment variables after your Lambda function is created, you must create your own AWS KMS key and choose it instead of the default key. The default key will give errors when chosen. Creating your own key gives you more flexibility, including the ability to create, rotate, disable, and define access controls, and to audit the encryption keys used to protect your data.

<img src="https://media.tutorialsdojo.com/2019-07-26_21-22-58-bc110e8ef8d91e32af6af839a0296911.png"
     alt="AWS KMS"
     width="600" />

Hence, the correct answer is: Create a new AWS KMS key and use it to enable encryption helpers that leverage on AWS Key Management Service to store and encrypt the sensitive information.

The option that says: There is no need to do anything because, by default, Lambda already encrypts the environment variables using the AWS Key Management Service is incorrect. Although Lambda encrypts the environment variables in your function by default, the sensitive information would still be visible to other users who have access to the Lambda console. This is because Lambda uses a default KMS key to encrypt the variables, which is usually accessible by other users. The best option in this scenario is to use encryption helpers to secure your environment variables.

The option that says: Enable SSL encryption that leverages on AWS CloudHSM to store and encrypt the sensitive information is also incorrect since enabling SSL would encrypt data only when in-transit. Your other teams would still be able to view the plaintext at-rest. Typically, AWS KMS is the recommended choice for encrypting sensitive data at rest.

The option that says: Lambda does not provide encryption for the environment variables. Deploy your code to an Amazon EC2 instance instead is incorrect since, as mentioned, Lambda does provide encryption functionality of environment variables.

</details>

## Question 4

**A government agency plans to store confidential tax documents on AWS. Due to the sensitive information in the files, the Solutions Architect must restrict the data access requests made to the storage solution to a specific Amazon VPC only. The solution should also prevent the files from being deleted or overwritten to meet the regulatory requirement of having a write-once-read-many (WORM) storage model.**

**Which combination of the following options should the Architect implement? (Select TWO.)**

- 🅐 Configure an Amazon S3 Access Point for the S3 bucket to restrict data access to a particular VPC only.
- 🅑 Store the tax documents in the Amazon S3 Glacier Instant Retrieval storage class. Use the `PutBucketPolicy` API to apply a bucket policy that restricts access requests to a specific VPC.
- 🅒 Set up a new Amazon S3 bucket to store the tax documents and integrate it with AWS Network Firewall. Configure the Network Firewall to only accept data access requests from a specific VPC.
- 🅓 Create a new Amazon S3 bucket with the S3 Object Lock feature enabled. Store the documents in the bucket and set the Legal Hold option for object retention.
- 🅔 Enable Object Lock but disable Object Versioning on the new Amazon S3 bucket to comply with the write-once-read-many (WORM) storage model requirement.

<details>
<summary><strong>Answer & Explanation</strong> 📝</summary>

### ✅ Correct Answers: 🅐 and 🅓

### 🅐 Configure an Amazon S3 Access Point to restrict access to a specific VPC

- **S3 Access Points** allow you to create **VPC-restricted access policies**.
- You can explicitly allow access **only from a specific VPC**, preventing any public or external access.
- This is the **recommended and simplest way** to enforce VPC-only access to S3.

### 🅓 Enable S3 Object Lock with Legal Hold for WORM compliance

- **S3 Object Lock** provides **WORM (write-once-read-many)** protection.
- **Legal Hold** prevents objects from being **deleted or overwritten**, regardless of retention period.
- This feature is specifically designed to meet **regulatory and compliance requirements** for immutable storage.

- ❌ **🅔 Disable Object Versioning**
  **Object Lock requires Object Versioning to be enabled**. You cannot disable versioning and still use Object Lock.

---

### Key takeaway 📌

To meet **both VPC-only access** and **WORM compliance** requirements for sensitive government data:

👉 Use **Amazon S3 Access Points (VPC-restricted)**
👉 Enable **Amazon S3 Object Lock with Legal Hold**

**A car dealership website hosted in Amazon EC2 stores car listings in an Amazon Aurora database managed by Amazon RDS. Once a vehicle has been sold, its data must be removed from the current listings and forwarded to a distributed processing system.**

**Which of the following options can satisfy the given requirement?**

- 🅒 Create an RDS event subscription and send the notifications to Amazon SNS. Configure the SNS topic to fan out the event notifications to multiple Amazon SQS queues. Process the data using AWS Lambda functions.

**Create a native function or a stored procedure that invokes an AWS Lambda function, which then sends messages to Amazon SQS.**

### Explanation

The key requirement here is **row-level / application-level events**:

- A vehicle is **sold**
- The record is **removed from current listings**
- The data must be **forwarded to a distributed processing system**

This is **business logic**, not an infrastructure or database-instance event.

### Why 🅐 is correct

- **Amazon Aurora** supports invoking **AWS Lambda functions directly** using native functions or stored procedures.
- This allows you to:

  - React **immediately when a row changes** (for example, when a car is marked as sold)
  - Execute logic **inside the database transaction**

- The Lambda function can then:

  - Send a message to **Amazon SQS**
  - Decouple the database from downstream distributed processing systems

This design is:

- Event-driven
- Loosely coupled
- Scalable
- Aligned with application-level data changes

  RDS event subscriptions are used for:

  - Instance start/stop
  - Failovers

  - Maintenance events

  They **do NOT capture row-level data changes** (such as “a car was sold”).

- ❌ **Using SNS/SQS fan-out with RDS events**
  Even though the messaging architecture is valid, the **event source itself is wrong** for this use case.

### Key takeaway 📌

- **Use RDS/Aurora native Lambda integration** for **data-level events**
- **Use RDS event subscriptions** only for **infrastructure and operational events**

👉 For application data changes that must trigger downstream processing, **Aurora → Lambda → SQS** is the correct solution.

## Question 6

**An online shopping platform is hosted on an Auto Scaling group of Amazon EC2 Spot Instances and utilizes Amazon Aurora PostgreSQL as its database. It is required to optimize database workloads in the cluster by directing the production traffic to high-capacity instances and routing the reporting queries from the internal staff to low-capacity instances.**

**Which is the most suitable configuration for the application as well as the Aurora database cluster to achieve this requirement?**

- 🅐 Configure your application to use the reader endpoint for both production traffic and reporting queries, which will enable your Aurora database to automatically perform load-balancing among all the Aurora Replicas.
- 🅑 Do nothing since by default, Aurora will automatically direct the production traffic to your high-capacity instances and the reporting queries to your low-capacity instances.
- 🅒 Create a custom endpoint in Aurora based on the specified criteria for the production traffic and another custom endpoint to handle the reporting queries.
- 🅓 In your application, use the instance endpoint of your Aurora database to handle the incoming production traffic and use the cluster endpoint to handle reporting queries.

<details>
<summary><strong>Answer & Explanation</strong> 📝</summary>

### ✅ Correct Answer: 🅒

**Create a custom endpoint in Aurora for production traffic and another custom endpoint for reporting queries.**

### Explanation

The key requirement is **workload isolation and traffic steering**:

- **Production traffic** must go to **high-capacity instances**
- **Reporting queries** must go to **low-capacity instances**
- The solution must be **explicit and controllable**

**Amazon Aurora Custom Endpoints** are designed exactly for this use case.

With custom endpoints, you can:

- Define **which instances (or instance classes)** belong to each endpoint
- Route **write-heavy or latency-sensitive production traffic** to larger instances
- Route **read-heavy reporting queries** to smaller, cost-efficient replicas
- Update membership dynamically without changing application code

---

### Why the other options are incorrect

- ❌ **🅐 Reader endpoint for both workloads**
  Reader endpoints **load-balance reads across all replicas** and do not allow you to control which instances receive which type of traffic.

- ❌ **🅑 Do nothing**
  Aurora does **not automatically differentiate workloads** based on capacity or intent. Explicit configuration is required.

- ❌ **🅓 Instance endpoint + cluster endpoint**
  The **cluster endpoint** always points to the **writer**, making it unsuitable for reporting queries. This also does not provide workload segregation.

### Key takeaway 📌

When you need **fine-grained control over how different workloads are routed within an Aurora cluster**, the correct solution is:

👉 **Amazon Aurora Custom Endpoints**

Amazon Aurora typically involves a cluster of DB instances instead of a single instance. Each connection is handled by a specific DB instance. When you connect to an Aurora cluster, the host name and port that you specify point to an intermediate handler called an endpoint. Aurora uses the endpoint mechanism to abstract these connections. Thus, you don't have to hardcode all the hostnames or write your own logic for load-balancing and rerouting connections when some DB instances aren't available.

For certain Aurora tasks, different instances or groups of instances perform different roles. For example, the primary instance handles all data definition language (DDL) and data manipulation language (DML) statements. Up to 15 Aurora Replicas handle read-only query traffic.

<img src="https://media.tutorialsdojo.com/2019-04-03_00-40-18-850e58ca7802358579be53729bfc0cbb.gif"
     alt="Aurora Cluster"
     width="600" />

Using endpoints, you can map each connection to the appropriate instance or group of instances based on your use case. For example, to perform DDL statements you can connect to whichever instance is the primary instance. To perform queries, you can connect to the reader endpoint, with Aurora automatically performing load-balancing among all the Aurora Replicas. For clusters with DB instances of different capacities or configurations, you can connect to custom endpoints associated with different subsets of DB instances. For diagnosis or tuning, you can connect to a specific instance endpoint to examine details about a specific DB instance.

The custom endpoint provides load-balanced database connections based on criteria other than the read-only or read-write capability of the DB instances. For example, you might define a custom endpoint to connect to instances that use a particular AWS instance class or a particular DB parameter group. Then you might tell particular groups of users about this custom endpoint. For example, you might direct internal users to low-capacity instances for report generation or ad hoc (one-time) querying, and direct production traffic to high-capacity instances.

The option that says: In your application, use the instance endpoint of your Aurora database to handle the incoming production traffic and use the cluster endpoint to handle reporting queries is incorrect because a cluster endpoint (also known as a writer endpoint) for an Aurora DB cluster simply connects to the current primary DB instance for that DB cluster. This endpoint can perform write operations in the database such as DDL statements, which is perfect for handling production traffic but not suitable for handling queries for reporting since there will be no write database operations that will be sent. Moreover, the endpoint does not point to lower-capacity or high-capacity instances as per the requirement. A better solution for this is to use a custom endpoint.

</details>

## Question 8

**A company is using a combination of Amazon API Gateway and AWS Lambda for the web services of an online web portal that is accessed by hundreds of thousands of clients each day. The company will be announcing a new revolutionary product, and it is expected that the web portal will receive a massive number of visitors from all around the globe.**

**How can the back-end systems and applications be protected from traffic spikes?**

- 🅐 API Gateway will automatically scale and handle massive traffic spikes so you do not have to do anything.
- 🅑 Deploy Multi-AZ in API Gateway with Read Replica.
- 🅒 Manually upgrade the Amazon EC2 instances being used by API Gateway.
- 🅓 Use throttling limits in API Gateway.

<details>
<summary><strong>Answer & Explanation</strong> 📝</summary>

### ✅ Correct Answer: 🅓

**Use throttling limits in API Gateway**

### Explanation

Although **Amazon API Gateway and AWS Lambda automatically scale**, protecting **back-end systems** from sudden traffic spikes requires **explicit traffic control**.

**API Gateway throttling** allows you to:

- Set **rate limits** (requests per second)
- Define **burst limits** to handle short traffic spikes
- Prevent downstream systems (Lambda, databases, third-party APIs) from being overwhelmed
- Apply limits **per API, per stage, or per API key**

This ensures:

- Fair usage across clients
- Protection against accidental or malicious request floods
- Predictable back-end performance during high-traffic events

### Why the other options are incorrect

- ❌ **🅐 Do nothing**
  While API Gateway scales automatically, **uncontrolled traffic can still overwhelm back-end dependencies** such as databases or third-party services.

- ❌ **🅑 Multi-AZ with Read Replica**
  API Gateway is already a **fully managed, multi-AZ service**. Read replicas are not applicable to API Gateway.

- ❌ **🅒 Upgrade EC2 instances**
  API Gateway does **not run on customer-managed EC2 instances**, so this option is invalid.

### Key takeaway 📌

To **protect back-end systems from massive traffic spikes** when using API Gateway and Lambda:

👉 **Configure throttling limits in Amazon API Gateway**

Amazon API Gateway provides throttling at multiple levels including global and by a service call. Throttling limits can be set for standard rates and bursts. For example, API owners can set a rate limit of 1,000 requests per second for a specific method in their REST APIs, and also configure Amazon API Gateway to handle a burst of 2,000 requests per second for a few seconds.

<img src="https://media.tutorialsdojo.com/New-API-GW-Diagram.c9fc9835d2a9aa00ef90d0ddc4c6402a2536de0d.png"
     alt="API Gateway Throttling"
     width="600" />

Amazon API Gateway tracks the number of requests per second. Any requests over the limit will receive a 429 HTTP response. The client SDKs generated by Amazon API Gateway retry calls automatically when met with this response.

Hence, the correct answer is: Use throttling limits in API Gateway.

The option that says: API Gateway will automatically scale and handle massive traffic spikes so you do not have to do anything is incorrect. Although it can scale using AWS Edge locations, you still need to configure the throttling, typically to further manage the bursts of your APIs.

The option that says: Manually upgrade the Amazon EC2 instances being used by API Gateway is incorrect because API Gateway is a fully managed service and hence, you do not have access to its underlying resources.

The option that says: Deploying Multi-AZ in API Gateway with Read Replica is incorrect because only RDS has Multi-AZ and Read Replica capabilities, and not API Gateway.

</details>

**A popular social media website uses an Amazon CloudFront web distribution to serve static content to millions of users around the globe. The manager has instructed the team to significantly reduce login time and further optimize the system.**

- 🅐 Customize the content that the CloudFront web distribution delivers to users using **Lambda@Edge**, which allows AWS Lambda functions to execute the authentication process in AWS locations closer to the users.
- 🅑 Establish multiple Amazon VPCs in different AWS Regions and configure a transit VPC to interconnect all resources. Deploy AWS Lambda functions in each Region using AWS SAM.

<details>
<summary><strong>Answer & Explanation</strong> 📝</summary>

### ✅ Correct Answer: 🅒

**Implement a canary release deployment strategy for the API Gateway.**

### Explanation

The key requirements are:

- **Minimal customer disruption**
- **Minimal data loss**
- **Most cost-effective approach**
- Existing **regional API Gateway with a custom domain**

**API Gateway canary deployments** are purpose-built for this scenario:

- Allow you to deploy a **new API version to a canary stage**
- Route a **small, controlled percentage of traffic** to the new version
- Continuously **monitor errors, latency, and behavior**
- Gradually increase traffic only after validation
- Instantly roll back by reducing canary traffic to 0%

This ensures:

- Very low blast radius if issues occur
- Near-zero disruption to end users
- No need to duplicate full API Gateway infrastructure

---

### Why blue-green is not the most cost-effective here

- **Blue-green deployments** require running **two full production environments** in parallel.
- This increases cost and operational complexity.
- Canary deployments achieve the same safety goals **using a single API Gateway**.

### Why the other options are risky

- ❌ **🅐 New API Gateway + same domain**
  Causes a hard cutover and DNS dependency, increasing disruption risk.

- ❌ **🅑 Import-to-update on existing API**

- Fast rollback
- Lowest cost and risk
