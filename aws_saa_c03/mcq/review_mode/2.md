## Question 1

**A media company has two VPCs: VPC-1 and VPC-2 with a peering connection between each other. VPC-1 only contains private subnets while VPC-2 only contains public subnets. The company uses a single AWS Direct Connect connection and a private virtual interface to connect their on-premises network with VPC-1.**

**Which of the following options increase the fault tolerance of the connection to VPC-1? (Select TWO.)**

* 🅐 Establish a hardware VPN over the Internet between **VPC-1** and the on-premises network.
* 🅑 Establish a hardware VPN over the Internet between **VPC-2** and the on-premises network.
* 🅒 Establish another AWS Direct Connect connection and private virtual interface in the same AWS Region as **VPC-1**.
* 🅓 Establish a new AWS Direct Connect connection and private virtual interface in the same region as **VPC-2**.
* 🅔 Use AWS VPN CloudHub to create a new AWS Direct Connect connection and private virtual interface in the same region as **VPC-2**.

<details>
<summary>Answer & Explanation</summary>

### ✅ Correct Answers: 🅐 and 🅒

---

### 🅐 Establish a hardware VPN over the Internet between VPC-1 and the on-premises network

* This provides an **Internet-based backup path** if the Direct Connect link fails.
* AWS best practice is to use a **Site-to-Site VPN as a failover** for Direct Connect.
* When Direct Connect is unavailable, traffic can automatically fail over to the VPN.
* This directly increases the **fault tolerance of the connection to VPC-1**, which is the VPC connected to on-premises.

---

### 🅒 Establish another AWS Direct Connect connection and private virtual interface in the same AWS Region as VPC-1

* A **single Direct Connect connection is a single point of failure**.
* Adding a second Direct Connect connection (ideally in a different DX location) provides **physical redundancy**.
* Using another **private virtual interface to VPC-1** ensures continued connectivity even if one DX link or location fails.
* This is the **most robust and recommended high-availability design** for Direct Connect.

---

### ❌ Why the other options are incorrect

* ❌ **🅑 VPN to VPC-2**
  The on-premises network is connected to **VPC-1**, not VPC-2.
  A VPN to VPC-2 does **not directly improve fault tolerance to VPC-1**.

* ❌ **🅓 Direct Connect to VPC-2**
  The requirement is to improve resiliency for **VPC-1 connectivity**.
  Connecting Direct Connect to VPC-2 does not solve the primary failure domain.

* ❌ **🅔 AWS VPN CloudHub**
  VPN CloudHub is used for **hub-and-spoke VPN connectivity between multiple remote sites**, not for Direct Connect redundancy or VPC fault tolerance.

---

### Key takeaway 📌

To improve fault tolerance for Direct Connect–based connectivity to a VPC:

👉 **Use a Site-to-Site VPN as a backup path AND provision multiple Direct Connect connections to the same VPC.**

This aligns with AWS best practices for **high availability and resilience**.

</details>

## Question 2

**A company is hosting its web application in an Auto Scaling group of EC2 instances behind an Application Load Balancer (ALB). Recently, the Solutions Architect identified a series of SQL injection attempts and cross-site scripting (XSS) attacks against the application, which have adversely affected production data.**

**Which of the following should the Architect implement to mitigate this kind of attack?**

* 🅐 Set up security rules that block SQL injection and cross-site scripting attacks in AWS Web Application Firewall (WAF) and associate the rules with the Application Load Balancer.
* 🅑 Use Amazon GuardDuty to prevent any further SQL injection and cross-site scripting attacks in the application.
* 🅒 Block all IP addresses from which SQL injection and XSS attacks originated using a Network Access Control List (NACL).
* 🅓 Use AWS Firewall Manager to set up security rules that block SQL injection and cross-site scripting attacks and associate the rules with the ALB.

<details>
<summary>Answer & Explanation</summary>

### ✅ Correct Answer: 🅐

**Use AWS Web Application Firewall (WAF) with rules to block SQL injection and cross-site scripting (XSS) attacks and associate it with the Application Load Balancer.**

---

### Explanation

The problem describes **Layer 7 (application-layer) attacks**, specifically:

* **SQL Injection**
* **Cross-Site Scripting (XSS)**

These attacks exploit **HTTP request patterns**, not network-level access.

**AWS WAF** is purpose-built to:

* Inspect **HTTP/HTTPS requests**
* Detect and block **SQLi and XSS patterns**
* Protect applications behind **ALB, CloudFront, and API Gateway**
* Apply **managed rule groups** (OWASP Top 10) or custom rules

By associating AWS WAF directly with the **Application Load Balancer**, malicious requests are blocked **before they reach the EC2 instances**, protecting application data immediately.

---

### ❌ Why the other options are incorrect

* ❌ **Amazon GuardDuty**
  GuardDuty is a **threat detection service**, not a prevention service. It identifies suspicious activity but **does not block requests**.

* ❌ **Network ACLs (NACLs)**
  Operate at **Layer 3/4 (IP and port level)**. They cannot inspect HTTP payloads and are ineffective against SQLi/XSS.

* ❌ **AWS Firewall Manager**
  Firewall Manager is used for **centralized policy management** across multiple accounts.
  It does **not replace AWS WAF** and still requires WAF rules underneath. For a single application, WAF alone is sufficient.

---

### Key takeaway 📌

To mitigate **SQL injection and XSS attacks** on applications behind an ALB:

👉 **Use AWS WAF with managed or custom rules and associate it with the Application Load Balancer.**

This is the **correct, immediate, and AWS-recommended security control** for application-layer attacks.

</details>

## Question 3

**A company has an application that continually sends encrypted documents to Amazon S3. The company requires that the configuration for data access is in line with its strict compliance standards. It should also be alerted if there is any risk of unauthorized access or suspicious access patterns.**

**Which step is needed to meet the requirements?**

* 🅐 Use Amazon Rekognition to monitor and recognize patterns on S3.
* 🅑 Use Amazon GuardDuty to monitor malicious activity on S3.
* 🅒 Use Amazon Inspector to alert whenever a security violation is detected on S3.
* 🅓 Use AWS CloudTrail to monitor and detect access patterns on S3.

<details>
<summary>Answer & Explanation</summary>

### ✅ Correct Answer: 🅑

**Use Amazon GuardDuty to monitor malicious activity on Amazon S3.**

---

### Explanation

The requirements are:

* **Continuous monitoring** of access to encrypted data in Amazon S3
* Detection of **unauthorized or suspicious access patterns**
* **Automated alerts** when risks are identified
* Alignment with **security and compliance standards**

**Amazon GuardDuty** is the correct service because:

* It provides **threat detection**, not just logging
* Continuously analyzes:

  * **AWS CloudTrail data events for S3**
  * VPC Flow Logs
  * DNS logs
* Detects **anomalous and malicious behaviors**, such as:

  * Unusual data access patterns
  * Suspicious API calls
  * Potential credential compromise
* Generates **security findings and alerts** automatically

This directly satisfies the requirement to be **alerted about risks**, not just record access.

---

### Why the other options are incorrect

* ❌ **Amazon Rekognition**
  Used for image and video analysis. It has nothing to do with S3 access monitoring or security.

* ❌ **Amazon Inspector**
  Designed for **vulnerability scanning** of EC2 instances, containers, and Lambda functions — not S3 access behavior.

* ❌ **AWS CloudTrail**
  Records **who did what and when**, but:

  * It does **not analyze behavior**
  * It does **not generate alerts for suspicious patterns** by itself
    CloudTrail is a **data source**, which GuardDuty uses under the hood.

---

### Key takeaway 📌

When you need:

* **Continuous security monitoring**
* **Detection of suspicious or unauthorized access to S3**
* **Automated alerts for compliance and security risks**

👉 **Amazon GuardDuty** is the correct and AWS-recommended solution.

</details>

## Question 4

**A company has a static corporate website hosted in a standard Amazon S3 bucket and a new web domain name that was registered using Amazon Route 53. There is a requirement to integrate these two services in order to successfully launch the corporate website.**

**What are the prerequisites when routing traffic using Route 53 to a website that is hosted in an S3 bucket? (Select TWO.)**

* 🅐 The S3 bucket must be in the same region as the hosted zone.
* 🅑 The S3 bucket name must be the same as the domain name.
* 🅒 A registered domain name.
* 🅓 The record set must be of type MX.
* 🅔 The Cross-Origin Resource Sharing (CORS) option should be enabled in the S3 bucket.

<details>
<summary>Answer & Explanation</summary>

### ✅ Correct Answers: 🅑 and 🅒

* **The S3 bucket name must be the same as the domain name**
* **A registered domain name**

---

### Explanation

When hosting a **static website on Amazon S3** and routing traffic to it using **Amazon Route 53**, there are specific prerequisites that must be met.

---

### 🅑 The S3 bucket name must be the same as the domain name

* For **S3 static website hosting**, the bucket name must **exactly match the domain name** (for example, `example.com`).
* This is required because Route 53 uses an **Alias record** that points to the S3 website endpoint, which is tied to the bucket name.
* Without this naming match, Route 53 cannot correctly route traffic to the S3 website endpoint.

---

### 🅒 A registered domain name

* You must own or register a **domain name** (for example, through Route 53 or another registrar).
* This domain is used to create a **hosted zone** and DNS records that route user traffic to the S3 website.

---

### ❌ Why the other options are incorrect

* ❌ **🅐 Same region as the hosted zone**
  Route 53 is a **global service**. Hosted zones are not tied to a specific AWS region.

* ❌ **🅓 MX record**
  MX records are used for **email routing**, not for websites.

* ❌ **🅔 CORS enabled**
  CORS is only needed for **browser-based cross-origin requests**, not for routing traffic to a static website.

---

### Key takeaway 📌

To route traffic from Route 53 to an S3 static website:

👉 You must have a **registered domain name** and an **S3 bucket whose name exactly matches that domain**.

</details>

## Question 5

**A company is running a dashboard application on a Spot EC2 instance inside a private subnet. The dashboard is reachable via a domain name that maps to the private IPv4 address of the instance’s network interface. A Solutions Architect needs to increase network availability by allowing traffic to resume on another instance if the primary instance is terminated.**

**Which solution accomplishes these requirements?**

* 🅐 Set up AWS Transfer for FTPS service in Implicit FTPS mode to automatically disable the source/destination checks on the instance’s primary elastic network interface and reattach it to another instance.
* 🅑 Use AWS Network Firewall to detach the instance’s primary elastic network interface and move it to a new instance upon failure.
* 🅒 Attach an Elastic IP address to the instance’s primary network interface and move it to a secondary instance using AWS Transit Gateway.
* 🅓 Create a secondary elastic network interface (ENI) and point its private IPv4 address to the application’s domain name. Attach the ENI to the primary instance. If the instance goes down, move the ENI to another instance.

<details>
<summary>Answer & Explanation</summary>

### ✅ Correct Answer: 🅓

**Create a secondary elastic network interface (ENI) and move it to another instance on failure.**

---

### Explanation

Key facts from the scenario:

* The application runs in a **private subnet**
* The domain name maps to a **private IPv4 address**
* The instance is a **Spot EC2 instance**, which can be **terminated at any time**
* High availability is required **without changing the DNS record**

---

### Why 🅓 is correct

* **Elastic Network Interfaces (ENIs)** have **persistent private IP addresses**.
* A **secondary ENI** can be:

  * Attached to one EC2 instance
  * Detached and **re-attached to another instance in the same subnet**
* Since the domain name already points to the **private IP of the ENI**, traffic resumes immediately after reattachment.
* This avoids DNS changes and provides **fast failover**.
* This pattern is commonly used for **active/passive failover inside private subnets**.

This solution works perfectly with **Spot Instances**, where termination is expected.

---

### ❌ Why the other options are incorrect

* ❌ **🅐 AWS Transfer for FTPS**
  Unrelated service. It has nothing to do with EC2 networking or failover.

* ❌ **🅑 AWS Network Firewall**
  Network Firewall filters traffic but **cannot move ENIs between instances**.

* ❌ **🅒 Elastic IP + Transit Gateway**

  * Elastic IPs are for **public IP addressing**, not private-only access.
  * Transit Gateway does **not manage ENI or EIP failover**.
  * Adds unnecessary complexity and does not meet the private subnet requirement.

---

### Key takeaway 📌

When:

* An application uses a **private IP**
* Fast failover is required
* DNS changes should be avoided

👉 **Use a secondary ENI with a stable private IP and move it to another EC2 instance on failure.**

This is the **simplest, fastest, and most reliable solution** for private-subnet high availability.

</details>

## Question 6

**A company has an on-premises MySQL database that needs to be replicated into Amazon S3 as CSV files. The database will eventually be launched to an Amazon Aurora Serverless cluster and integrated with an RDS Proxy to allow web applications to pool and share database connections. Once data has been fully copied, the ongoing changes to the on-premises database should be continually streamed into the S3 bucket. The company wants a solution that can be implemented with little management overhead yet is still highly secure.**

**Which ingestion pattern should a solutions architect take?**

* 🅐 Create a full load and change data capture (CDC) replication task using AWS Database Migration Service (AWS DMS). Add a new Certificate Authority (CA) certificate and create an AWS DMS endpoint with SSL.
* 🅑 Use an AWS Snowball Edge cluster to migrate data to Amazon S3 and AWS DataSync to capture ongoing changes. Create a custom AWS KMS envelope encryption key.
* 🅒 Set up a full load replication task using AWS Database Migration Service (AWS DMS). Launch an AWS DMS endpoint with SSL using AWS Network Firewall.
* 🅓 Use AWS Schema Conversion Tool (AWS SCT) to convert MySQL data to CSV files and AWS Application Migration Service (AWS MGN) to capture ongoing changes.

<details>
<summary>Answer & Explanation</summary>

### ✅ Correct Answer: 🅐

**Create a full load and change data capture (CDC) replication task using AWS Database Migration Service (AWS DMS) with SSL-enabled endpoints.**

### Explanation

The requirements are very clear:

* Initial **full data load** from on-premises MySQL
* **Continuous streaming of ongoing changes** (CDC)
* Target is **Amazon S3 in CSV format**
* **Low operational overhead**
* **High security**

**AWS Database Migration Service (AWS DMS)** is purpose-built for exactly this ingestion pattern.

![AWS DMS](https://media.tutorialsdojo.com/aws-dms-tutorialsdojo-SSL-endpoint-saa-c03.png)

### Why AWS DMS with Full Load + CDC is the best choice

* **Full load + CDC** allows:

  * One-time bulk copy of existing data
  * Continuous replication of ongoing changes
* AWS DMS natively supports:

  * **MySQL as a source**
  * **Amazon S3 as a target**
  * Output in **CSV format**
* **Minimal management overhead**:

  * Fully managed service
  * No need to manage servers or custom pipelines
* **High security**:

  * SSL/TLS encryption for endpoints
  * Support for customer-managed CA certificates
  * IAM-based access control

This approach also aligns well with the future plan to migrate into **Amazon Aurora Serverless**, as DMS is commonly used in database modernization workflows.

---

### Why the other options are incorrect

* ❌ **🅑 Snowball + DataSync**
  Snowball is designed for **large offline data transfers**, not continuous CDC. DataSync also does not support database-level change data capture.

* ❌ **🅒 Full load only with DMS**
  Does not meet the requirement for **continuous streaming of changes**. Network Firewall is also unrelated to DMS endpoint encryption.

* ❌ **🅓 AWS SCT + AWS MGN**

  * AWS SCT is for **schema conversion**, not data replication
  * AWS MGN is for **server migration**, not database CDC or S3 ingestion

---

### Key takeaway 📌

For **secure, low-maintenance ingestion of on-premises database data into Amazon S3 with ongoing change replication**:

👉 **AWS DMS with Full Load + CDC and SSL-enabled endpoints** is the correct and AWS-recommended solution.

</details>

## Question 7

**All objects uploaded to an Amazon S3 bucket must be encrypted for security compliance. The bucket will use server-side encryption with Amazon S3–managed encryption keys (SSE-S3) to encrypt data using the 256-bit Advanced Encryption Standard (AES-256) block cipher.**

**Which of the following request headers must be used?**

* 🅐 `x-amz-server-side-encryption-customer-key`
* 🅑 `x-amz-server-side-encryption`
* 🅒 `x-amz-server-side-encryption-customer-algorithm`
* 🅓 `x-amz-server-side-encryption-customer-key-MD5`

<details>
<summary>Answer & Explanation</summary>

### ✅ Correct Answer: 🅑 `x-amz-server-side-encryption`

---

### Explanation

The requirement explicitly states:

* **Server-side encryption**
* **Amazon S3–managed keys**
* **AES-256 encryption**
* **SSE-S3**

For **SSE-S3**, the client must include the following request header when uploading an object:

```
x-amz-server-side-encryption: AES256
```

This tells Amazon S3 to:

* Encrypt the object using **AES-256**
* Manage the encryption keys **entirely by S3**
* Automatically handle key storage and rotation

---

### Why the other options are incorrect

* ❌ **`x-amz-server-side-encryption-customer-key`**
  Used only for **SSE-C (customer-provided keys)**.

* ❌ **`x-amz-server-side-encryption-customer-algorithm`**
  Also specific to **SSE-C**, where the customer supplies the encryption algorithm.

* ❌ **`x-amz-server-side-encryption-customer-key-MD5`**
  Used to provide an MD5 checksum of a **customer-provided key** (SSE-C).

---

### Key takeaway 📌

* **SSE-S3 → `x-amz-server-side-encryption: AES256`**
* **SSE-KMS → `x-amz-server-side-encryption: aws:kms`**
* **SSE-C → customer-key–related headers**

For this scenario, **only `x-amz-server-side-encryption` is required**.

> ⚠️ Note (2026): Since **5 Jan 2023**, S3 encrypts every new object with SSE-S3 by default. So today the header is optional for SSE-S3. The exam answer is still `x-amz-server-side-encryption`.

</details>
