## Question 1

**A company has launched multiple Amazon EC2 instances inside a private subnet of a VPC. The Solutions Architect is reviewing the Network ACL (NACL) inbound rules associated with that subnet to ensure security. The current Inbound Rules for the NACL are configured as follows:**

![https://udemy-images.s3.amazonaws.com/redactor/raw/2018-02-03_09-36-25-e4a7214623d1499d801d9fe0f021596a.png](https://udemy-images.s3.amazonaws.com/redactor/raw/2018-02-03_09-36-25-e4a7214623d1499d801d9fe0f021596a.png)

A computer with the IP address 110.238.109.37 attempts to send a request to one of the EC2 instances in this subnet.

What will happen to the incoming request based on the NACL rules?

**Options:**

- Initially, it will be denied and then after a while, the connection will be allowed.
- It will be denied.
- Initially, it will be allowed and then after a while, the connection will be denied.
- It will be allowed.

<details>
  <summary><strong>Answer & Explanation</strong> 📝</summary>

### ✅ Correct Answer

**It will be allowed.**

### 📝 Explanation

Network ACL (NACL) rules are evaluated **in ascending order of rule number**, starting from the lowest. The **first matching rule** is applied, and evaluation stops immediately.

From the inbound rules shown:

- **Rule 100**:

  - Type: ALL Traffic
  - Source: `0.0.0.0/0`
  - Action: **ALLOW**

This rule allows **all inbound traffic from any IP address**, including `110.238.109.37`. Since this rule matches first, AWS **does not evaluate any subsequent rules**.

Even though:

- **Rule 101** explicitly **DENIES TCP traffic on port 4000 from `110.238.109.37/32`**,
  it is **never reached**, because Rule 100 already allowed the traffic.

**The `*` rule is evaluated after rule 100.**

In **AWS Network ACLs**, rule evaluation follows these strict rules:

- Rules are processed **in ascending order of rule number** (lowest to highest).
- The rule marked with `*` is the **implicit default rule**.
- The `*` rule is **always evaluated last**, regardless of how it appears visually in the console.

In the given NACL:

- **Rule 100** → ALLOW all traffic from `0.0.0.0/0`
- **Rule 101** → DENY TCP port 4000 from `110.238.109.37/32`
- **Rule `*`** → DENY all traffic (default rule)

Because rule **100** is evaluated first and already allows the traffic:

- AWS **stops evaluation immediately**
- Rule **101** and the `*` rule are **never reached**

### ❌ Why the other options are incorrect

- <span style="color:red"><strong>Initially, it will be denied and then after a while, the connection will be allowed – Incorrect</strong></span>
  NACLs are **stateless** but they do **not change behavior over time**. There is no concept of “initially” or “after a while”.

- <span style="color:red"><strong>It will be denied – Incorrect</strong></span>
  The deny rule (Rule 101) is overridden by the earlier allow rule (Rule 100).

- <span style="color:red"><strong>Initially, it will be allowed and then after a while, the connection will be denied – Incorrect</strong></span>
  NACLs do not track connections or sessions, so behavior does not change mid-connection.

### 🧠 Key Takeaway

- **NACL rules are processed in order**
- **First match wins**
- A broad **ALLOW** rule placed before a specific **DENY** rule will make the deny rule ineffective

</details>

## Question 2

**A company needs to collect gigabytes of data per second from websites and social media feeds to gain insights on its product offerings and continuously improve the user experience. To meet this design requirement, an application hosted on an Auto Scaling group of Spot EC2 instances processes the data and stores the results in DynamoDB and Amazon Redshift. The solution should have a built-in enhanced fan-out feature. Which fully managed AWS service can collect and process large streams of data records in real time with the LEAST amount of administrative overhead?**

**Options:**

- AWS Data Exchange
- Amazon S3 Access Points
- Amazon Kinesis Data Streams
- Amazon Managed Streaming for Apache Kafka (Amazon MSK)

<details>
  <summary><strong>Answer & Explanation</strong> 📝</summary>

### ✅ Correct Answer

**Amazon Kinesis Data Streams**

### 📝 Explanation

**Amazon Kinesis Data Streams** is purpose-built for **real-time data ingestion and processing at massive scale** with **minimal operational overhead**.

Key reasons it is the correct choice:

- Supports **gigabytes per second** of streaming data ingestion
- Provides **built-in Enhanced Fan-Out (EFO)**, allowing multiple consumers to read the same stream **independently and in parallel** with low latency
- Fully managed by AWS — no need to manage brokers, partitions, or clusters
- Integrates natively with **EC2, DynamoDB, Redshift, Lambda, and analytics services**

This directly matches the requirement for:

- Real-time processing
- Built-in enhanced fan-out
- Least administrative effort

### ❌ Why the other options are incorrect

- <span style="color:red"><strong>AWS Data Exchange – Incorrect</strong></span>
  Used for **subscribing to and sharing third-party datasets**, not real-time stream ingestion.

- <span style="color:red"><strong>Amazon S3 Access Points – Incorrect</strong></span>
  Simplifies access control for S3 buckets but is **not a streaming or real-time ingestion service**.

- <span style="color:red"><strong>Amazon Managed Streaming for Apache Kafka (Amazon MSK) – Incorrect</strong></span>
  Although powerful, MSK requires **cluster sizing, partition planning, and ongoing operational management**, resulting in **higher administrative overhead** compared to Kinesis Data Streams.
  Also, **enhanced fan-out is a native Kinesis feature**, not Kafka.

### 🧠 Summary

- **Enhanced fan-out** → Native to **Kinesis Data Streams**
- **Least admin overhead** → Kinesis (serverless-style management)
- **High-throughput, real-time streaming** → Kinesis fits best

## Question 3

To save storage costs, the company plans to copy all the application data to AWS while retaining the ability to retrieve data with the same low-latency access as the local file share. The company does not have the capacity to develop custom tools for this operation. Which of the following should the company use?**

**Options:**

- AWS Virtual Private Network (VPN)
- AWS Storage Gateway
- AWS Snowball Edge
- Amazon FSx for Windows File Server

<details>
  <summary><strong>Answer & Explanation</strong> 📝</summary>

### ✅ Correct Answer

**AWS Storage Gateway**

### 📝 Explanation

The scenario describes a **hybrid storage requirement**:

- On-premises application using **SMB file shares**
- Most data should be stored **cost-effectively in AWS**
- Frequently accessed data must still be available with **low latency**
- **No custom development** should be required

**AWS Storage Gateway (File Gateway)** fits perfectly:

- Presents a **native SMB file share** to on-premises servers
- Stores data durably in **Amazon S3** (low-cost storage)
- Frequently accessed data is **cached locally**, providing **low-latency access**
- Fully managed by AWS, requiring **minimal administration**
- Designed specifically for **on-premises to AWS hybrid file storage**

### ❌ Why the other options are incorrect

- <span style="color:red"><strong>AWS Virtual Private Network (VPN) – Incorrect</strong></span>

  FSx provides an SMB file system **inside AWS**, but it does **not cache data on-premises**. Accessing it would introduce network latency and does not meet the “same low-latency as local file share” requirement.

### 🧠 Key Takeaways

- **SMB + on-premises + AWS + caching** → **AWS Storage Gateway (File Gateway)**
- **Low latency for hot data** → Local cache

## Question 4

**A company is deploying a Microsoft SharePoint Server environment on AWS using CloudFormation. The architecture includes Microsoft Active Directory (AD) domain controllers, Microsoft SQL Server 2012, multiple EC2 instances for SharePoint, and other dependencies. The Solutions Architect must ensure that the required components are properly installed and running before the CloudFormation stack creation proceeds. What should the Architect do to meet this requirement?**

**Options:**

- Configure the **DependsOn** attribute in the CloudFormation template. Send a success signal after the applications are installed and configured using the `cfn-init` helper script.
- Configure a **CreationPolicy** attribute to the instance in the CloudFormation template. Send a success signal after the applications are installed and configured using the `cfn-signal` helper script.
- Configure an **UpdatePolicy** attribute to the instance in the CloudFormation template. Send a success signal after the applications are installed and configured using the `cfn-signal` helper script.
- Configure the **UpdateReplacePolicy** attribute in the CloudFormation template. Send a success signal after the applications are installed and configured using the `cfn-signal` helper script.

<details>
  <summary><strong>Answer & Explanation</strong> 📝</summary>

### ✅ Correct Answer

**Configure a `CreationPolicy` attribute to the instance in the CloudFormation template and send a success signal using the `cfn-signal` helper script after installation and configuration are complete.**

### 📝 Explanation

This scenario requires **CloudFormation to wait** until complex software installations (AD, SQL Server, SharePoint, etc.) are **fully installed and running** before marking the resource — and therefore the stack — as successfully created.

This is exactly what **`CreationPolicy` + `cfn-signal`** is designed for:

- **`CreationPolicy`**

  - Tells CloudFormation to **pause resource creation**
  - Waits for a defined number of **success signals**

- **`cfn-signal`**

  - Explicitly notifies CloudFormation that the instance setup is **complete and healthy**

- Ensures stack creation **does not proceed or succeed prematurely**

This pattern is commonly used for **Windows-based, multi-step application deployments** like SharePoint.

### ❌ Why the other options are incorrect

- <span style="color:red"><strong>DependsOn – Incorrect</strong></span>
  `DependsOn` only controls **resource creation order**, not whether software inside an EC2 instance is **fully installed and running**.

- <span style="color:red"><strong>UpdatePolicy – Incorrect</strong></span>
  `UpdatePolicy` applies only during **stack updates**, not initial creation.

- <span style="color:red"><strong>UpdateReplacePolicy – Incorrect</strong></span>
  `UpdateReplacePolicy` controls what happens to resources **when they are replaced**, not stack creation readiness.

### 🧠 Key Takeaways

- Need CloudFormation to **wait for application readiness** → use **`CreationPolicy`**
- Need explicit success notification → use **`cfn-signal`**
- `DependsOn` ≠ readiness check
- `UpdatePolicy` and `UpdateReplacePolicy` ≠ creation-time validation

</details>

- Create an AWS Backup plan to take daily snapshots with a retention period of 90 days.
- Configure an automated backup and set the backup retention period to 90 days.
- Configure RDS to export the automated snapshot automatically to Amazon S3 and create a lifecycle policy to delete the object after 90 days.

<details>
  <summary><strong>Answer & Explanation</strong> 📝</summary>

### ✅ Correct Answer

**Create an AWS Backup plan to take daily snapshots with a retention period of 90 days.**

### 📝 Explanation

Amazon Aurora (and Amazon RDS in general) has a **hard limit** on automated backup retention:

- **Automated backups support a maximum retention period of 35 days**

Since the requirement is **90 days**, native automated backups **cannot** satisfy this requirement.

**AWS Backup** solves this limitation:

- Centrally manages backups for Aurora and other AWS services
- Allows **custom retention periods**, including **90 days or more**
- Fully managed and requires **no custom scripting**
- Meets compliance and long-term retention requirements

### ❌ Why the other options are incorrect

- <span style="color:red"><strong>Configure an automated backup and set the backup retention period to 90 days – Incorrect</strong></span>
  Aurora automated backups **cannot exceed 35 days**, so this option is not technically possible.

- <span style="color:red"><strong>Configure RDS to export the automated snapshot automatically to Amazon S3 and create a lifecycle policy – Incorrect</strong></span>
  Automated snapshot exports to S3 are **not supported in this manner**, and this adds unnecessary complexity.

- <span style="color:red"><strong>Use CloudWatch Events and Lambda to download snapshots to S3 and archive to Glacier – Incorrect</strong></span>
  This approach requires **custom development and maintenance**, which is unnecessary when AWS Backup provides a native solution.

### 🧠 Key Takeaways

- **Aurora automated backups max retention = 35 days**
- **90-day retention** → must use **AWS Backup**
- Prefer **managed services** over custom automation for backup compliance

</details>

## Question 8

**A solutions architect is writing an AWS Lambda function that will process encrypted documents from an Amazon FSx for NetApp ONTAP file system. The documents are protected by an AWS KMS customer-managed key. After processing, the Lambda function stores the results in an S3 bucket using the Amazon S3 Glacier Flexible Retrieval storage class. The architect must ensure that the Lambda function can decrypt the files. Which action accomplishes this requirement?**

**Options:**

- Attach the `kms:Decrypt` permission to the Lambda function’s **resource policy**. Add a statement to the AWS KMS key policy that grants the function’s **resource policy ARN** the `kms:Decrypt` permission.
- Attach the `kms:Decrypt` permission to the Lambda function’s **execution role**. Add a statement to the AWS KMS key policy that grants the function’s **execution role** the `kms:Decrypt` permission.
- Attach the `kms:Decrypt` permission to the Lambda function’s **resource policy**. Add a statement to the AWS KMS key policy that grants the function’s **execution role** the `kms:Decrypt` permission.
- Attach the `kms:Decrypt` permission to the Lambda function’s **execution role**. Add a statement to the AWS KMS key policy that grants the function’s **ARN** the `kms:Decrypt` permission.

<details>
  <summary><strong>Answer & Explanation</strong> 📝</summary>

### ✅ Correct Answer

**Attach the `kms:Decrypt` permission to the Lambda function’s execution role and add a statement to the AWS KMS key policy that grants the function’s execution role the `kms:Decrypt` permission.**

### 📝 Explanation

When AWS Lambda accesses encrypted data (from FSx, S3, or other services), it does so **using its execution role**, not its resource policy.

To successfully decrypt data encrypted with a **customer-managed KMS key**, **both** of the following must be true:

1. **IAM permission**

   - The Lambda function’s **execution role** must allow `kms:Decrypt`.

2. **KMS key policy permission**

   - The **KMS key policy** must explicitly trust (allow) the **same execution role** to use `kms:Decrypt`.

Only when **both IAM policy and KMS key policy align** will decryption succeed.

> ⚠️ Correction: the key policy must allow the role **either directly or by letting IAM policies grant access**. The default key policy (the "Enable IAM User Permissions" statement for the account) already lets IAM policies grant access, so with it the IAM policy alone is enough. Naming the role in the key policy is the safe answer when the key policy does not have that statement.

### ❌ Why the other options are incorrect

- <span style="color:red"><strong>Execution role not referenced in KMS key policy – Incorrect</strong></span>
  KMS always checks its **key policy first**. Granting permissions only in IAM works only if the key policy lets IAM policies grant access (the default key policy does).

- <span style="color:red"><strong>Using Lambda resource policy – Incorrect</strong></span>
  Lambda resource policies control **who can invoke the function**, not what AWS services the function can access.

- <span style="color:red"><strong>Granting permission to the Lambda function ARN – Incorrect</strong></span>
  KMS permissions must be granted to **IAM principals (roles or users)**, not directly to a Lambda function ARN.

### 🧠 Key Takeaways

- Lambda accesses AWS services using its **execution role**
- **KMS checks two places**:

  - IAM policy on the role
  - The **KMS key policy** (an explicit allow, or the default statement that lets IAM policies grant access)

- Resource policies ≠ permissions to access KMS-encrypted data

</details>

## Question 9

**An online registration system hosted in an Amazon EKS cluster stores data in a `db.t4g.medium` Amazon Aurora DB cluster. The database performs well during regular hours but cannot handle traffic surges during flash sales. A solutions architect must move the database to Aurora Serverless while minimizing downtime and impact on application operations. Which change should be taken to meet the objective?**

**Options:**

- Change the Aurora instance class to Serverless
- Add an Aurora Replica to the cluster and set its instance class to Serverless. Fail over to the read replica and promote it to primary.
- Take a snapshot of the DB cluster. Use the snapshot to create a new Aurora DB cluster.
- Use AWS Database Migration Service (AWS DMS) to migrate to a new Aurora Serverless database.

<details>
  <summary><strong>Answer & Explanation</strong> 📝</summary>

### ✅ Correct Answer

**Add an Aurora Replica to the cluster and set its instance class to Serverless. Fail over to the read replica and promote it to primary.**

> ⚠️ Correction (2026): this file used to give **AWS DMS** as the answer. That was based on Aurora Serverless **v1**, which reached end of life on 31 Mar 2025. With Aurora Serverless **v2**, AWS documents the replica + failover path below as the way to switch a provisioned cluster.

### 📝 Explanation

Aurora Serverless **v2** uses the `db.serverless` **instance class**. A cluster can mix provisioned and Serverless v2 instances. So the documented, low-downtime way to switch is:

- Set the Serverless v2 capacity range (min/max ACU) on the existing cluster.
- **Add a reader** with the `db.serverless` instance class.
- **Fail over** to that reader. It becomes the writer. The only downtime is the short failover.
- Optionally convert or remove the old provisioned instances.

No new cluster, no data copy, and no DMS task are needed.

### ❌ Why the other options are incorrect

- <span style="color:red"><strong>Change the Aurora instance class to Serverless – Incorrect</strong></span>
  You *can* modify an instance to `db.serverless` in Serverless v2. But changing the **writer** in place restarts it, so the database is down during the change. Adding a reader and failing over has less downtime.

- <span style="color:red"><strong>Use AWS DMS to migrate to a new Aurora Serverless database – Incorrect</strong></span>
  It works, but it needs a second cluster, a replication task and an application cutover. It is more work and more risk than a failover inside the same cluster.

- <span style="color:red"><strong>Snapshot and restore – Incorrect</strong></span>
  Restoring from a snapshot requires **full downtime** during the cutover and does not meet the “minimize downtime” requirement.

### 🧠 Key Takeaways

- Aurora Serverless v2 = the `db.serverless` instance class inside a normal Aurora cluster
- Provisioned → Serverless v2: **add a Serverless v2 reader, then fail over**
- Failover gives only a short interruption
- AWS DMS is for moving to a **different** cluster or engine, not needed here

</details>

- Use Dedicated EC2 instances to ensure that each instance has the maximum performance possible.
- Add multiple Elastic Fabric Adapters (EFA) to each EC2 instance to increase the network bandwidth.

<details>
  <summary><strong>Answer & Explanation</strong> 📝</summary>

### ✅ Correct Answers

- **Use Dedicated EC2 instances to ensure that each instance has the maximum performance possible.**
- **Add multiple Elastic Fabric Adapters (EFA) to each EC2 instance to increase the network bandwidth.**

### 📝 Explanation

The question focuses specifically on **DDoS mitigation** for a **public-facing application**. The two selected options are **not suitable** because they do **not provide any DDoS protection**.

- **Elastic Fabric Adapter (EFA)** is designed for **low-latency, tightly coupled HPC workloads** (e.g., MPI jobs) and **does not help defend against volumetric or application-layer DDoS attacks**.

- <span style="color:red"><strong>Use Amazon CloudFront – NOT Incorrect</strong></span>
  CloudFront distributes traffic globally, **absorbs large attack volumes**, and integrates with **AWS Shield and WAF**.

### 🧠 Key Takeaways

- **DDoS mitigation ≠ performance optimization**
- **EFA and Dedicated EC2** are HPC performance features, not security controls
- Effective DDoS defense uses:

  - AWS Shield
  - AWS WAF
  - CloudFront
  - ALB + Auto Scaling

- Public-facing workloads must prioritize **traffic absorption and filtering**, not raw bandwidth

## Question 14

**An aerospace engineering company is launching an Amazon VPC with both public and private subnets. The Solutions Architect must ensure that each subnet is properly defined within the VPC CIDR block. Which of the following statements are true regarding VPC subnets? (Select TWO.)**

**Options:**

- Each newly created subnet is, by default, linked to the main route table of the VPC.
- Each subnet maps to a single Availability Zone.
- EC2 instances in a private subnet can communicate with the Internet only if they have an Elastic IP.
- The allowed block size in VPC is between a /16 netmask (65,536 IP addresses) and /27 netmask (32 IP addresses).
- Each subnet spans 2 Availability Zones.

<details>
  <summary><strong>Answer & Explanation</strong> 📝</summary>

### ✅ Correct Answers

- **Each newly created subnet is, by default, linked to the main route table of the VPC.**
- **Each subnet maps to a single Availability Zone.**

### 📝 Explanation

- **Default route table association**
  When a subnet is created in a VPC, it is automatically associated with the **main route table** unless you explicitly associate it with a custom route table.

- **Single Availability Zone mapping**
  A subnet is always created **within one and only one Availability Zone**. Subnets **do not span multiple AZs**, which is a core AWS design principle for high availability.

### ❌ Why the other options are incorrect

- <span style="color:red"><strong>Private subnet EC2 instances need an Elastic IP to access the Internet – Incorrect</strong></span>
  Instances in a private subnet access the Internet using a **NAT Gateway or NAT instance**, not an Elastic IP on the instance itself.

- <span style="color:red"><strong>Allowed block size in VPC is /16 to /27 – Incorrect</strong></span>
  The smallest allowed block is **/28 (16 IP addresses)**, not /27. Both the VPC CIDR and each IPv4 subnet can be between **/16 and /28**.

- <span style="color:red"><strong>Each subnet spans 2 Availability Zones – Incorrect</strong></span>
  Subnets **never span multiple AZs**.

### 🧠 Key Takeaways

- Subnets are **AZ-specific**
- New subnets automatically associate with the **main route table**
- Private subnet Internet access requires **NAT**, not Elastic IP
- Understanding subnet–AZ boundaries is critical for resilient VPC design

</details>
